1.1 地址与入口#

项值说明

页面来源宿主机静态文件 /srv/platform/apps/museframe/data/web/admin.html（只读挂进容器）后台页面不在镜像里，换页面与换后端是两件事（见 第 6 节）

1.2 凭据在哪里#

后台只有一个凭据：ADMIN_TOKEN。它唯一的存放处是生产机上的 app.env（权限 600）。读取命令：

ssh prodsrv "sudo grep ^ADMIN_TOKEN= /srv/platform/apps/museframe/app.env"
纪律：令牌值不要贴进聊天窗口、工单、文档或截图。只确认「配了没有」用这条： 
ssh prodsrv "sudo grep -c ^ADMIN_TOKEN= /srv/platform/apps/museframe/app.env"   # 回 1 = 已配置

登录框里粘进令牌点「进入」即可。令牌作为请求头 X-Admin-Token 发送，服务端用恒定时间比对。

令牌不进 URL。 页面上的 CSV 导出与图片预览都走 fetch + blob，不用 <a download> 或 window.open——浏览器发起的导航带不上请求头，那样的链接一律回 401。所以不要把管理接口地址直接粘到浏览器地址栏，那样永远是 401。

1.3 会话时长与登出#

项值
凭据存放浏览器 sessionStorage（键 mf.admin），按标签页隔离
有效期服务端不发会话票，所以「会话」就是这个标签页的寿命：关掉标签页 / 关掉浏览器即失效
历史遗留页面启动时会主动清掉旧版写在 localStorage 里的持久副本（持久保存过的令牌是个风险面）
登出关掉标签页；或任何接口回 401 时页面会自动清掉令牌并弹回登录框，提示「令牌不正确或已过期」
换令牌的副作用改 ADMIN_TOKEN 并重新 deploy 之后，所有打开着的后台标签页下一次请求即 401

1.4 安全说明#

  1. 管理接口限频 120 次 / 分钟（按 /v1/admin/ 前缀整体计）。超了回 429。
  2. 后台没有任何密钥写入口。 image_provider_api_key 与 smtp_pass 在配置页只显示掩码，写它们直接回 422——这是对 Node 版「从后台设一次上游密钥，密钥就明文躺进数据库并随每日备份落盘」那个问题的修复，属有意的行为变更。
  3. 数据库浏览页只读：查询台只接受单条 SELECT / WITH，密钥列已脱敏，部分表不可查。
  4. CSV 导出一律脱敏（邮箱打码、id 只给前 8 位），理由是导出文件会离开这台机器。
  5. 每一次写操作都落审计（改配置 / 改商品 / 改风格 / 禁用启用用户 / 发额度 / 重试 / 重验 / 标已处理）。

2.1 九个标签页#

顶部是一条标签栏，URL 里的 #hash 就是当前标签（可直接收藏，例如 admin.html#config）。右上角「刷新」只重载当前标签。

#tab-users用户读 + 手动发额度 + 禁用 / 启用

#tab-assets资产只读

2.2 每个视图一句说明#

概览 #overview

  • 顶部两条横幅：① 生成链路——现在到底能不能产出一张图，判据是最近真实上游调用的结果，不是「配置齐不齐」；② 反白嫖闸——免费额度的 IP / 全站日配额有没有被顶到。
  • 卡片：累计用户、累计收入等盘子数。
  • 生成任务：可按状态（queued / running / quality_check / succeeded / failed / cancelled）、时间窗、用户 ID 前 8 位筛；带生成参数与上游返回摘要；失败 / 取消的行上有「重试」。
  • 购买记录：平台 / 交易号 / 金额 / 入账额度，可按状态（只有 pending 与 verified 两个值）与平台筛；verified 的行上有「重验」。
  • 用户反馈：含用户写的正文，可按好评 / 差评与处理状态筛，行上有「标已处理」。

用户 #users

  • 手动加额度：按发件邮箱或完整用户 ID 充值，走正规账本（source_type = manual），备注可在数据库页的 manual_grants 表里查。
  • 状态分布卡片：各状态账号数、会话有效期、「禁用拦住了什么」。
  • 用户列表：可按邮箱 / 显示名 / ID 搜（搜索串按字符截到 120），每行可禁用 / 启用，可点开单用户纵向详情（额度账本 / 购买 / 项目 / 任务 / 资产 / 会话六块）。

统计 #stats

按天趋势：每日生成（成功/失败）、每日新增用户、每日收入（按购买记录的 amount_minor 汇总，美分），以及风格排行（按累计生成次数）——用它决定下架谁、把谁挪到展架前面。

埋点 #events

App 的 POST /v1/events 上报。四块：按事件名、按 App 版本、按天、原始样本。窗口 7/30/90 天（上限 90）。 「按 App 版本」正常结果是一行「(未上报)」——App 当前的 track() 不带版本字段，这一行就是这件事的唯一可见处（后端已兼容 appVersion/app_version/version 三种键，App 哪天开始报都会自动分开）。 审计与发信记录也住在 events 表里，但埋点视图把这两类行排掉了，否则运营自己改一次配置都会在「用户行为」里多一行。

资产 #assets

App 上传的源图与产出文件。可按类型（source / candidate / thumbnail / export）、状态（pending / ready / quarantined / deleted）、用户 ID 前 8 位筛；带字节数 / 宽高 / sha256；顶部是合计卡片。图片预览走短时图片令牌，管理员令牌不进 URL。

健康 #health

  • 接口健康：窗口可选，上限 24 小时。详见 3.10。
  • 邮件发送记录：验证码信与后台测试邮件的发送台账，地址打码。刻意不记主题与正文——验证码信的主题以明文验证码开头，记下来等于一条账号接管旁路。
  • 验证码签发台账：签发了哪些码（不回哈希）。

运营 #ops

  • 风格管理：用户在 App 首页看到的那张卡片（名称 / 副标题 / 主题 / 是否付费专属 / 位次 / 标签 / 状态）。行序就是用户看到的顺序。「App 可见」列比「状态」更重要。
  • 商品与价格：改价与上下架立刻反映到 /v1/products，不需要发版。
  • 反馈原因码：这是观测不是配置——原因码是 App 里写死的四个差评芯片，服务端不做枚举校验，App 也不读服务端字典。要增删原因码得发 App 版本。
  • 操作审计：后台每一次写操作一行。审计住在 events 表里，会被保留期清理一起删（天数见 4.1 的 event_retention_days，下界刻意是 7 天）。

数据库 #db

只读翻库：左侧选表分页浏览，下面的查询台只接受单条 SELECT / WITH。密钥列已脱敏。 这一页是全后台唯一展示 UTC 的地方（显示库里原始列值，ISO-8601 带 Z）；其余页面一律北京时间 UTC+8。这里改不了任何数据——要改去对应功能页，那样才有审计。

配置 #config

  • 顶部重复那两条横幅（生成链路 / 反白嫖闸）。
  • 运行状态：七张只读卡片，详见 3.10 B。
  • 系统配置：41 个热键按 8 个分组渲染，每组顶上一句说明；每项标来源徽章（db 覆盖 / env / 默认）、是否需重启、是否只读。
  • 邮件测试：发一封自检信，结果留在页面上。

2.3 时区与脱敏的统一口径#

口径内容
时区后端一切时间戳是 UTC；除「数据库」页外，所有页面统一换算成北京时间（UTC+8）展示并标出来
用户 ID列表里只显示前 8 位。多数筛选框接受 8 位前缀；前缀撞车时接口回 409 AMBIGUOUS，这时要填完整 id
邮箱列表页显示完整（只有持令牌的人打得开）；CSV 导出一律打码，脱敏点只有一处
密钥任何页面只给「已配置 / 未配置」或掩码

3 · 日常任务（逐步骤 + 预期结果）#

3.1 优惠码 / 注册码：MuseFrame 没有这条路#

MuseFrame 后端与后台没有注册码 / 优惠码 / 兑换码功能，34 条管理路由里没有任何一条与码有关。不要在面板上找它，也不要答应用户「给你发个码」。

等价的运营动作是手动发额度（见 3.2 C）：它走正规额度账本，可填备注与有效期，并落审计。需要「码」这种离线可发货的形态时，那是掌镜 Zlens 的能力，不是 MuseFrame 的。

3.2 账号：查看 / 禁用 / 发额度 / 撤销 / 删号#

A. 查看一个用户的全部事实

  1. 进 用户 → 搜索框填邮箱 / 显示名 / ID → 回车。
  2. 点这一行进「单用户纵向详情」。 预期结果：一页里给出六块——额度账本、购买、项目（含软删行）、任务、资产、会话。

用 8 位前缀查就够了；撞前缀时回 409 AMBIGUOUS，这时填完整 ID。

B. 禁用 / 启用一个账号

  1. 用户 列表里点这一行的「禁用」。
  2. 必须填原因（≤300 字）。 没有原因的封禁在三个月后等于「不知道为什么这个人进不来」，而客服收到的投诉里只有一句「我登不上」。
  3. 提交。预期结果：该账号的所有令牌立刻按「未登录」处理，任何接口回 401；运营 · 操作审计 多一行（含从什么状态改到什么状态 + 原因）。
  4. 撤销：点「启用」。 预期结果：会话行没删过，原令牌立刻恢复可用；作品与额度台账一律没动——这是个可逆动作。
异常返回含义
422「禁用账号必须填写原因」原因留空了
422「status 只能是 active 或 suspended」请求被改过，刷新页面重试
404 Unknown userid 不存在或已软删

C. 手动发额度（客服最常做的动作）

  1. 进 用户 → 顶部「手动加额度」。
  2. 填邮箱或完整用户 ID（用户额度用完时 App 会展示客服邮箱，也就是配置里的 support_email，所以你通常手上有的是他的发件邮箱）。
  3. 填张数：1..10000。
  4. 有效期（天）可空 = 不过期；填则 1..3650。
  5. 填备注（≤300 字，例如「微信转账 ¥xx / 邮件日期」）。
  6. 提交。预期结果：页面回显发放结果与该用户的新可用余额；账本里多一笔 source_type = manual；数据库页 manual_grants 表能查到备注；审计多一行。
异常返回含义 / 处置
422 units must be an integer between 1 and 10000张数越界
422 expiresInDays must be … 1 and 3650有效期越界；要「不过期」请留空而不是填 0
422 Provide userId or email两个都空
409 AMBIGUOUSID 前缀撞车，填完整 ID
409 幂等键不匹配同一个幂等键上次发的是别的内容。换一个键或确认上次是否已成功

D. 撤销额度 / 删号

后台没有「撤销额度」与「删号」按钮。额度账本是只增的分录式台账（发放 / 预留 / 释放都是独立分录），所以「撤销」的正确做法是记清原因后不再发放，或由开发按分录补一笔——不要去数据库页手改（那里改不了，也不该改：直接改库没有审计）。账号注销需求请走开发，当前没有自助入口。

3.3 反馈与来信：处理与回复#

后台不代发邮件。 SMTP 那条路只用于发登录验证码与后台测试信。回复用户要用你自己的邮箱；后台这里做的是标记与登记。
  1. 进 概览 → 「用户反馈」，筛「处理状态 = 未处理」。旁边有未处理条数。
  2. 读正文（用户真的写了什么）与评价（👍/👎）。差评带原因码时一并看。
  3. 需要联系用户：去 用户 按 id 查出邮箱，用自己的邮箱回信。
  4. 回到这一行点「标已处理」，填备注（你做了什么 / 回了什么）。 预期结果：该行 handled_at / handled_note 有值，从「未处理」筛选里消失；审计多一行。
  5. 标错了就再点一次取消。 注意：撤销标记会把备注一起清掉——留着上一次的备注会让下一个人看到「未处理」却带着一条「已退额度」的备注，而这两件事里只有一件是真的。
异常返回含义
422「handled 必填」/「handled 必须是布尔值」请求被改过，刷新重试
404 Unknown feedback row这条反馈已被保留期清理或 id 不对
崩溃 / 日志上报这一页不存在，因为 App 里没有任何崩溃上报调用，后端也没有对应路由。做一页空表会让人以为「没崩过」。同理 App 不上报版本号，所以埋点的版本维度只有「(未上报)」。

3.4 任务重试与购买重验#

A. 重试一个失败的生成任务

  1. 进 概览 → 「生成任务」，状态筛 failed（或 cancelled）。
  2. 先看这一行的错误信息与上游返回摘要——如果是上游挂了，重试只会再花一次钱。先看 配置 · 运行状态 的「上游图像供应」卡片。
  3. 点「重试」。 预期结果：接口回新任务 id、父任务 id、本次预留张数与该用户剩余可用额度；列表里多一条新任务（状态 queued），旧那条原样保留为 failed；审计多一行。
重试是「新建一条任务」而不是「把原任务改回 queued」，这是刻意的：失败时额度走的是补偿分录（钱已经退给用户了），原地重排会让两个守卫都放行而一分不扣，净结果是一张免费的图，且额度对账表上看不出任何异常。
用户不会被重复扣钱：失败退过一次、重试扣回来，净额仍是「成功一张扣一份」。新任务的 parent_job_id 指向被重试那条，列表上的「重试次数」就是数它。
异常返回含义 / 处置
409「只有 failed / cancelled 的任务能重试（当前：…）」这条还在跑。重试在跑的任务会变成两个任务抢同一个项目的结果，而运营看不出哪个赢了
409 INSUFFICIENT_ENTITLEMENT这个用户额度不够。先去 3.2 C 发额度再重试——悄悄跳过扣减就等于回到那张免费图
404 Unknown jobid 不对

B. 重验一笔购买（用户说「我付了钱但张数没到」）

  1. 进 概览 → 「购买记录」，按平台或交易号找到那一笔。
  2. 确认它的状态是 verified。
  3. 点「重验」。 预期结果：缺失的额度被补发（幂等，重复点不会多发）；用户详情里的额度账本多一笔；审计多一行。如果额度本来就发过了，返回会说明没有需要补发的东西。
「重验」不会重新向商店要收据。 purchaseToken 只存在于 App 那一次请求里，从不落库，所以「重新找 Google/Apple 验一次」在服务端做不到。它做的是对着幂等键 grant:purchase:<purchaseId> 先查再发。
purchases.status 的词汇表只有 pending 与 verified，没有 active。状态是 pending 的那笔钱没验过，重验对它不生效。

3.5 风格编辑与紧急下架#

A. 改一个风格的可运营字段

  1. 进 运营 → 「风格管理」。行序就是用户在 App 首页看到的顺序（排序键 = 展览 editorial_rank + 位次）。
  2. 可改的字段只有这几个：
    字段限制说明
    名称 name非空，≤80 字只有一列（public_name），没有多语言列——要给中文用户看中文就直接改成中文
    副标题 shortCaption≤140 字，可为空目录卡片上的一行副标题，留空是合法的排版选择
    主题 theme非空，≤40 字—
    付费专属 premium布尔—
    位次 position0–9999决定在展架里的排位
    标签 tags字符串数组，每项 ≤40 字，有个数上限空串项被忽略、重复项去重
    状态 statuspublished / disabled与下面的上下架按钮写同一列
  3. 保存。预期结果：接口回更新后的整行，页面就地刷新；审计里记下改了哪几个字段。
「App 可见」那一列比「状态」更重要：状态是 published 但没有已发布版本、或者没挂在任何展览上，App 里一样看不到它。改完名字发现用户还看不见，先看这一列。

  2. 预期结果：目录查询只取 status='published'，所以 disabled 立刻在所有地方隐藏该风格（/v1/discover、/v1/styles）；审计多一行。

3.7 热配置：改与恢复#

A. 三级优先级

数据库覆盖 > 环境变量 > 代码默认值（密钥项除外，见下）。配置页每一项都带来源徽章，所以「这个值现在从哪来」是看得见的。

B. 改一项

  1. 进 配置 → 「系统配置」→ 找到分组里那一项，读它的说明与合法区间。
  2. 改值 → 保存。 预期结果：来源徽章变成 db 覆盖；页面重新拉一遍运行状态；审计里记下「从什么改成什么」。
  3. 生效时机：绝大多数键下一次使用即生效（并发数下一次 pump、模型名下一个任务、验证码有效期下一封信、保留期下一次清理任务、会话有效期只影响此后签发/续期的会话）。带 ⚠需重启 的项改了不会立刻生效。

C. 恢复成 env / 默认值

  1. 把那一项清空（页面提交 value: null）后保存。
  2. 预期结果：数据库覆盖被清掉，来源回到 env 或 默认，页面显示回退后的值；审计里这一条带 cleared 标记。
越界的值会被拒绝保存（422）而不是悄悄夹一下，错误信息里写着合法区间。读的一侧还会再夹一次——所以即使库里躺着 Node 版写下的越界行，服务也不会被打死，但那一项会在页面上挂一个 warning 提示「这个值被夹过」。看到 warning 就去把它改成区间内的值。

D. 哪些只能改 app.env + 重新 deploy

  1. 改文件（权限保持 600）：
    ssh prodsrv
sudo nano /srv/platform/apps/museframe/app.env
  2. 重新部署当前版本让容器重新读 env：
    sudo /srv/platform/scripts/platformctl deploy museframe --tag <当前生产 tag>
  3. 核对：
    sudo /srv/platform/scripts/platformctl status museframe
    预期结果：容器 healthy；配置页「后端版本 / 启动时间」卡片显示新的启动时间。
改 app.env 不重启不会生效；而 project.env / .env 只参与 compose 变量插值，不注入容器——容器环境严格由 compose 的 environment: 与经 env_file 载入的 app.env 决定。换版本、换密钥是两处要改的东西。

5 · 故障排查#

5.1 登录不上#

现象最可能的原因怎么确认 / 处置
输令牌回「令牌不正确或已过期」令牌不对，或复制时带了行尾 / 空格按 1.2 重新读一次
昨天还能进，今天不行① 标签页关过（令牌存在 sessionStorage，关掉即失效）；② 令牌被换过并 deploy 了重新粘一次令牌；仍然不行就重新读一次文件
页面一直「加载中…」，控制台一片 401同上重新登录
频繁 429管理接口 120 次/分钟；同一出口 IP 下有人跑脚本，或你在疯狂点刷新等一分钟
直接把接口地址粘地址栏，永远 401令牌走请求头，浏览器导航带不上不要这样用。导出和预览都从页面按钮走
admin.html 404宿主机 web 目录里的文件没了 / 路径不对ssh prodsrv "sudo ls /srv/platform/apps/museframe/data/web/admin.html"

5.2 状态码含义#

码含义典型场景与处置
401缺令牌 / 令牌错（AUTH_REQUIRED）所有 34 条管理路由无凭据一律 401。页面收到 401 会清掉令牌并弹回登录框。用它也能判断路由存不存在：401 = 路由存在，404 = 没这条路由
404对象不存在，或路径不在路由表里Unknown user / job / purchase / style / product / feedback row。也可能是这条记录已被保留期清理
409冲突，操作已放弃① AMBIGUOUS：8 位 id 前缀撞车 → 填完整 id；② 任务状态不允许重试（只有 failed / cancelled 能重试）；③ INSUFFICIENT_ENTITLEMENT：额度不够重试 → 先发额度；④ 幂等键不匹配
413超出单账号存储上限这是 App 侧上传时会遇到的码，判据是 max_user_storage_bytes。用户报「上传失败」先看资产页的该用户合计字节
422入参不合法（VALIDATION）后台里最常见的拒绝码：数值越界、枚举不在白名单、必填留空、写密钥键、SQL 查询台不是单条 SELECT/WITH。错误消息里写着合法区间或原因，照着改
429请求过快管理接口 120 次/分钟。限流的 429 在路由循环之前返回，所以不会出现在接口健康表里
502上游失败EMAIL_SEND_FAILED（SMTP 拒了）；生成链路的上游失败在任务行与运行状态卡片里看
412MuseFrame 后端不会回这个码看到 412 说明请求没走到应用（边缘 / CDN 层的条件请求）。先确认访问的是正式域名

5.3 数据显示「—」或空的原因#

在哪看到含义不是什么
接口健康表全是 0 / 空进程内计数，重启即清零。刚发过版就是这样不是「没有流量」也不是「没有错误」
接口健康里没有某条路径限流打回的请求不计；未匹配路由表的请求（扫描器、静态文件）一律不计不是漏了
P95 带 >落在最后一个开口桶里（精度到桶边界）不是精确值
「最近一次发送」显示「本进程还没发过信」重启后还没发过不是邮件坏了
埋点「按 App 版本」只有「(未上报)」App 的 track() 不带版本字段，这一行就是这件事的唯一可见处不是数据丢了
反馈原因码里有「未知码」通常来自老版本客户端（服务端不做枚举校验）不是脏数据要清
风格「状态 = published」但「App 可见 = 否」没有已发布版本，或没挂在任何展览上不是后台没保存成功
风格封面是空图封面是文件 web/covers/<internal_key>.jpg，不是数据库列不是数据缺列
商品在 App 里整条不见人民币价是 null（App 过滤掉没有人民币价的行）不是「退回显示美元价」
审计里查不到上个季度的记录审计住在 events 表里，会被 event_retention_days 清掉不是审计坏了。要留更久就把这个键调大（下界 7 天就是为这件事设的）
资产页 storage/ 目录 0 文件这是实测结果（2026-09-11 核对）不是探测失败
某个列表一直转圈先看运行状态的「数据库 / 连接池」卡片，池满（4/4）时请求变慢而不是报错多数情况下不是慢查询
生成全部失败看「上游图像供应」卡片与熔断状态。gpt.lenscript.cn 这条上游 9/5 起曾持续不可用，9/12 观测到变成 400 参数错，疑似恢复但未端到端实测确认不一定是本服务的问题
通用纪律：「没拿到数据」≠「数据是空的」。面板上每一处「—」「未配置」「本进程还没…」都是在区分这两件事，读的时候不要自己把它读成好消息。
