## 1. 严重（Critical）

### F01 — Google Play 购买重放：同一张收据可无限次兑换额度 ✅ 已修

**原因**：`verify.js` 用字符串拼接把 `purchaseToken` 塞进 Play API 的 URL 路径，
`api.js` 又拿**客户端原样传来的 token** 当 `purchases.external_transaction_id` 去重。
于是 `<token>?x=1`、`<token>#`、`<token>/`、把 `.` 换成 `%2E` …… 这些变体在 Google 那边
都解析成**同一笔购买**（Play 照常返回 valid），在我们库里却是**一条全新的交易**。
一次真实付款 → 无限次发放付费额度。

**修复**

| 位置 | 改动 |
|---|---|
| `server/verify.js:124` | `PLAY_TOKEN_RE = /^[A-Za-z0-9._-]{1,512}$/`——Google 的 token 是 URL-safe base64，字母表之外的一律不是合法 token |
| `server/verify.js:126` | `assertPlayToken(token, productId)`，`productId` 同样入 URL，同样校验 |
| `server/verify.js:182` | 调用 `assertPlayToken`，URL 里所有段一律 `encodeURIComponent` |
| `server/verify.js:213` | 返回 Google 自己签发的 `orderId` |
| `server/api.js:1013` | 进 Play 之前先 `assertPlayToken`，不合法直接 422 `VALIDATION` |
| `server/api.js:1047` | 拿到 `orderId` 后调 `adoptCanonicalTxId()`，**用 Google 的 orderId 而不是客户端字符串**去重 |
| `server/api.js:961` | `adoptCanonicalTxId()`：把 pending 行从 token 迁到 orderId；若 orderId 行已存在则删掉 token 占位行（两行都留 = 同一笔钱算两次） |
| `server/api.js:1063` | 购买写入 + `grantPurchaseUnits` 收进同一个 `tx()` |

**关键不变量**（测试固化）：凡是被接受的 token，`encodeURIComponent(t) === t`。
也就是「我们存下来的字节」和「Google 读到的字节」**在构造上必然相同**。

**测试**：`server/test/purchase-token.test.js`，24 例。14 种 URL 等价变体逐一验证被拒
（query / fragment / 尾斜杠 / `%2E` / `%2F` / 路径穿越 / 前导斜杠 / 尾空格 / 换行 / tab /
双 query / 分号参数 / Unicode 相似字符），外加 `adoptCanonicalTxId` 的 4 个去重场景。

## 2. 高危（High）

### F02 / F39 — 限流与免费额度 IP 上限建立在可伪造的头上 ✅ 已修

`clientIp` 取 `cf-connecting-ip || x-forwarded-for[0] || socket`，**前两者调用方随便写**。
每请求换一个随机值 ⇒ 全站限流形同虚设，包括 `/v1/auth/email/request` 的
「10 分钟 5 次」——那是一个**对任意邮箱的开放邮件炸弹**。

**修复**：新建 `server/net.js`（从 index.js 拆出，可脱离 HTTP 单测）。

- `makeClientIpResolver()`：**只有当 TCP 对端本身是可信代理时**才看转发头；
  看的时候**只取 `x-forwarded-for` 的最后一段**——那是可信代理自己追加的，
  也是调用方唯一改不了的一段（旧代码取 `[0]`，恰恰是纯客户端输入）。
- `cf-connecting-ip` **默认完全忽略**，需显式 `TRUST_CF_CONNECTING_IP=true`。
- `TRUSTED_PROXY` 默认 `private`（回环 + RFC1918 + ULA），正是当前拓扑：
  Caddy 在宿主机反代 `127.0.0.1:8787`，容器看到的对端是 docker 网桥网关。
- `server/index.js:103` `RL_MAX_KEYS`：限流表加上限，伪造 IP 不能再撑爆内存。

**实测**：`TRUSTED_PROXY=none` 下连发 8 个各带不同伪造 IP 的请求 → `501 501 501 501 501 429 429 429`，
第 6 个开始拦住，伪造完全失效。

**⚠️ 运维待办**：Caddy 必须是**追加**而非覆盖 `X-Forwarded-For`（Caddy `reverse_proxy` 默认就是追加，符合要求），
并在每个 site block 加 `header_up -CF-Connecting-IP` 剥掉客户端自带的同名头。详见 §7。

**测试**：`server/test/client-ip.test.js`，15 例。含「连发 500 个不同伪造头 → 限流器只看到 1 个桶」。

### F04 — 邮箱登录验证码用 `Math.random()` 生成 ✅ 已修（上一轮，已复核）

`Math.random()` 是 xorshift128+，**观察到少量输出即可反推内部状态**，而这个 6 位码是一张
完整的账号凭据（凭它能登录任意邮箱）。改为 `crypto.randomInt(100000, 1000000)`
（`server/api.js:453`）。同时 `server/api.js:492` 用 `timingSafeEqual` 比对哈希。

**测试**：`server/test/otp.test.js`，15 例。含「api.js 代码区（剥掉注释后）不得出现 `Math.random`」
——这条**当场抓出**我自己写的注释误报，也说明它是活的守卫。

### F03 / F15 — `ALLOW_TEST_LOGIN=true` 把明文验证码返回给任意匿名调用者 ✅ 已修（上一轮，已复核）

文档声称是「env 开关 + 管理员令牌」双重门禁，但 `devCode` 只看了 env 开关：
开着的话，**任何人**可以对**任意邮箱**要一次码然后直接读回来 = 全站账号接管。
现为 `if (testMode && isAdminRequest(...)) body.devCode = code`（`server/api.js:479`）。

**测试**：`otp.test.js` 断言全文件 `devCode =` 只出现一次且带门禁；`http.test.js` 实跑
「`?admin_token=` 走不通」。

### F05 / F13 — 免费额度重复发放（游客登录后再领一次）✅ 已修（上一轮，已复核）

去重键在游客期是设备哈希、登录后变成 user id，而合并保留同一个 user 行，
所以 user id 那把键**从来没被写进去过** → 同一台设备登录一次就再白拿一张。
现在 `maybeGrantFree`（`server/api.js:72`）把 `[dedupeId, deviceHash, userId]`
**全部查、全部写**，只有主键那行带 units（其余是记账行，`ledger.js` 的窗口统计
一律 `units > 0` 过滤，不会虚增 24h 上限）。

**测试**：`server/test/grants-controls.test.js`，含正反两个方向的合并场景。

### F11 — Play 订阅续期永远不发新额度 ✅ 已修（上一轮，已复核）

自动续订每期都会重放**同一个 purchaseToken**，旧代码见到已有行就 early-return，
于是第 2 期起既不发额度也不推 `expires_at`，`userPlan()` 把还在付钱的订阅者
降回 `free`。现按 `${purchaseId}:${expires}` 作为**按期幂等键**发放
（`ledger.js:31` 的 `referenceId` 参数 + `api.js:1073`）。

### F12 / F38 — 购买先落库、发额度在事务外 ✅ 已修

`grantedUnits = 0` 的商品会撞 `credit_buckets` 的 `CHECK (granted_units > 0)`，
但 `purchases` 那条 `verified` 已经提交了 → 钱收了、额度没发、重试还幂等返回 200。
现在 `INSERT/UPDATE purchases` 与 `grantPurchaseUnits` 在**同一个 `tx()`**里
（`api.js:1063`），且 `granted_units === 0` 直接跳过而非抛错（纯解锁型订阅是合法的）。

同一问题在生成任务上：任务行与 `reserveUnits` 原来是两个事务，中间崩溃就留下
「跑得起来但没扣费」的任务。现在合并为一个 `tx()`（`api.js:820`），
依赖 `db.js:353` 新增的**可重入 `tx()`**（内层 `tx` 并入外层，不再抛
"cannot start a transaction within a transaction"）。

**测试**：`ledger.test.js` 的 `tx() re-entrancy` 两例——内层抛错时整个工作单元回滚。

### F14 / F31 — worker 异常导致任务永久卡死且额度被锁 ✅ 已修

只有两个 adapter 调用被 try 包着。`readFileSync`（源图被删）、`JSON.parse`（脏 spec）、
`encodeJpeg`（OOM）或落盘段一抛，任务就永远停在 `running`/`quality_check`，
额度锁死，用户盯着一个永不前进的进度条，重启后还会**再跑一遍同样的崩溃**。

- `jobs.js:151` `processJob` 把状态检查之后的**全部逻辑**包进 try/catch，
  任何抛出都 `failJob(job, 'INTERNAL_ERROR')`（内部会 `releaseUnits` 退额度）。
- `jobs.js:100` `pump()` 的 `.catch` 作为最后一道防线：兜底把非终态任务判失败。
- `jobs.js:269` 落盘段单独包 try/catch，DB 写失败时**删掉已写出的孤儿文件**再抛。
- `jobs.js:145` 开跑前校验「必须存在 reserve 分录」，否则拒跑——丢失/回滚的扣费
  不能变成一张免费图。

### F32 — 恢复任务没有次数上限（崩溃循环 + 重复计费）✅ 已修

会 OOM 掉进程的任务每次开机都被重新入队 → 无限重启循环，而且**每一圈都是一次
真实的、要付钱的模型调用**。`jobs.js:18` `MAX_ATTEMPTS`（默认 3，`MAX_JOB_ATTEMPTS` 可调），
`recoverJobs` 与 `processJob` 双端拦截，超限直接判失败并退额度。

### F16 — 免费试用 / 变更套餐的订阅被判为无效 ✅ 已修

`paymentState === 1` 是「已收款」，但 **2 = 免费试用中、3 = 待生效的升降级**，
Google 认为这两类同样有权益。旧代码把他们全拒了。现为
`[1, 2, 3].includes(Number(body.paymentState))`（`verify.js:222`）。

### F17 — Play 侧的任何故障都报成 402「购买无效」 ✅ 已修

网络超时、Google 5xx、服务账号文件缺失、非 JSON 响应，全被翻译成
「你的购买是假的」——用户已经付过钱了。现在区分两类答案：

- `verify.js:109` `serviceAccount()` 读文件/解析失败 → `PROVIDER_NOT_CONFIGURED`
- `verify.js:165/200` fetch 抛错 → `PROVIDER_UNAVAILABLE`
- `verify.js:206` Google 5xx / 429 → `PROVIDER_UNAVAILABLE`；4xx 才是 `PURCHASE_INVALID`
- `api.js:1023` **先写 pending 行再问 Google**（钱已经收了，必须留一条可重试的记录）
- `api.js:1037` 「问不到」返回 **503 `VERIFICATION_UNAVAILABLE`**（可重试），
  只有「Google 说不」才落 402 `PURCHASE_INVALID`

> 契约说明：503 + `VERIFICATION_UNAVAILABLE` 是**新增**的失败分支，不是对已有码的改写。
> 客户端 `catch` 里 `PURCHASE_INVALID` / `PROVIDER_NOT_CONFIGURED` 之外走 else 分支，
> 提示「Purchase failed — you were not charged」，语义上是安全的降级。

### F27 — 任意匿名 POST 都能塞 26 MB 进内存 ✅ 已修

512 MB 的容器，没有并发上限，整包缓冲在 RAM，`/v1/events` 连会话都不要。

`server/net.js` 按路由分档：**只有** `PUT /v1/assets/:id/upload` 拿 26 MB，
`/v1/admin/*` 1 MB，其余 JSON 路由 **64 KB**。`Content-Length` 超限直接拒，不读 body。

### F28 / F07 — `events` 表可被匿名无限写入 ✅ 已修

`name` 会截断、`props` 不会——一个匿名 26 MB 请求原样入库，可按线速重复。

- `api.js:1129` 加 `requireUser(ctx)`
- `api.js:1135` `props` 序列化后超 2 KB 换成 `{truncated, bytes}`
- `index.js:82` 新增限流规则 `/v1/events` 120 次 / 10 分钟
- `db.js:295` 补 `events(name, occurred_at)` 索引
- `db.js:327` `pruneOldRows()`：启动时 + 每 24 小时清理 90 天前的遥测、
  过期会话、过期幂等记录、过期验证码，并跑 `PRAGMA optimize`

### F29 — 整图解码/编码在事件循环上同步执行 ⚠️ 部分修复

**已做**：`MAX_SOURCE_PIXELS = 40 MP`（`api.js:22`，超限 422 `ASSET_UNSUPPORTED`）；
`/complete` 把已解码的图**直接交给** `runAnalysis`，省掉第二次解码。
**未做**：搬进 `worker_threads` 线程池。那是一次架构改动（解码、分析、worker 三处调用点
都要改成异步 promise 协议），风险与「外科手术式修补」的定位不符。**留给运维决策**（§7）。

### F30 — 420s 超时是假的，300s 就被 undici 掐断 ⚠️ 部分修复

Node 的 fetch 自带 300s `headersTimeout`，进程内**无法调高**（要调必须引入 `undici` 依赖，
而本次约束是不加新依赖）。后果是：配了 420s，实际 300s 断线，**模型那边照样出图照样计费**，
我们收不到，还报成含糊的 `PROVIDER_ERROR`。

**已做**：`remoteAdapter.js:36` 把 `image_provider_timeout_ms` **夹到 290s**，
让后台面板、给用户看的「1–5 分钟」预估、和代码三者口径一致；
`remoteAdapter.js:119` 把 `UND_ERR_HEADERS_TIMEOUT` / `UND_ERR_BODY_TIMEOUT`
正确归类为 `PROVIDER_TIMEOUT`。**需要 >5 分钟的生成必须加 undici 依赖**——留给运维决策（§7）。

| F25 | 413 永远送不到客户端（先 destroy 了 socket） | ✅ | `index.js:47` 超限后**停止缓冲但继续限额丢弃读取**（≤8 MB / 5s），让请求正常收尾，413 能被完整读到；超出丢弃预算才断连。见下方说明 |
| F41 | 健康检查什么都不查 | ✅ | `api.js:1157` 探 DB（`quick_check` + 实查一次）、报生成可用性与队列深度；DB 探测失败返回 503 |
| F43 | 文档里的备份命令直接 tar 活动的 WAL 库（副本可能撕裂） | ✅ | `OPS.md` §6 改为 `VACUUM INTO` 一致性快照后再打包 |

**关于 F25 的一个实测发现**：最初按审计建议改成「停止读取 + 立刻回 413 + `Connection: close`」，
`curl` 能完整读到响应，但 **Node 自己的 `fetch`（undici）报 `fetch failed`**——请求体还在写
的时候连接被关，客户端读不到响应。这正是原 bug 的另一种形态。最终做法是
**限额排空**：超限即停止缓冲（内存才是要害），但继续读并丢弃，预算 `min(limit*4, 8 MB)` / 5 秒，
让请求正常 end 之后再写 413。内存有界、CPU 可忽略，而**任何客户端都能读到这个 413**。
`http.test.js` 里对 `Content-Length` 与 chunked 两种形态都做了验证。

## 7. 需要你（运维/Owner）拍板的事项

### 7.1 部署前**必须**做的

1. **轮换 `ADMIN_TOKEN`**。它此前既是管理员凭据，又被当作图片 HMAC 密钥和免费额度 IP 盐；
   默认值是空串（= 谁都能算出来的 HMAC key）。现在密钥已改由 `server_secrets` 表自动生成，
   但令牌本身**仍需轮换一次**，因为旧值可能出现在 `?admin_token=` 留下的历史日志里。
   注意：轮换会重置免费额度的 IP 计数（除非显式设了 `IP_HASH_SALT`）。
2. **Caddy 处理转发头**。每个 site block 加：
   ```
   reverse_proxy 127.0.0.1:8787 {
       header_up -CF-Connecting-IP
   }
   ```
   Caddy 默认**追加** `X-Forwarded-For`（符合要求，不用改）。
   另外建议：删掉 `http://museframe.43.155.234.117.nip.io` 这个明文直连入口，
   或限制到 Cloudflare 段——审计正是靠它绕过边缘的。
3. **`docker-compose.yml` 加 `stop_grace_period: 30s`**，与 `SHUTDOWN_GRACE_MS=25000` 配套，
   否则 SIGTERM 排空逻辑会被 docker 默认的 10 秒硬杀截断。
4. `.env` 补上新变量（`.env.example` 已写好带注释的模板，见下）。

### 7.2 需要你决定的

| 事项 | 选项 | 我的建议 |
|---|---|---|
| **Play acknowledge 语义** | Play 规定**3 天内未确认的购买自动退款**。服务端确认（`PLAY_ACKNOWLEDGE=true`）最稳妥，但如果客户端 `@capgo/native-purchases` 已在设备上确认/消费，重复确认会报错 | 先保持 `false` 上线，观察 WARN 日志里是否出现 `UNACKNOWLEDGED`。**如果出现就说明客户端没确认，必须立刻改成 `true`**，否则每一笔都会被 Google 退款 |
| **`TRUST_CF_CONNECTING_IP`** | 默认 `false`。若 Cloudflare 确实在前面，设为 `true` 能拿到真实客户端 IP（限流粒度更准）；但必须先做 7.1.2 的剥头 | 先 `false` 上线（安全侧保守）。确认 Caddy 剥头且源站不可绕过后再开 |
| **`>5 分钟`的生成** | Node fetch 硬顶 300s，突破必须加 `undici` 依赖并显式传 `dispatcher` | 现在夹到 290s。若实测确有超过 5 分钟的正常生成，再加这一个依赖；否则维持零依赖 |
| **图像处理搬进 worker_threads（F29）** | 当前解码/编码仍在主事件循环上，40 MP 封顶 | 单实例小流量下可接受。若并发上来后出现「进度轮询卡顿」，再做线程池 |
| **后台 SQL 控制台超时（F42）** | 一条 cross join 能冻住 HTTP 和 worker | 入口已收紧到 header-only 管理员令牌，风险面很小；如果要彻底解决，等 `node:sqlite` 支持 `readOnly` 后再做 |
| **`voidedpurchases` 退款巡检（F10 剩余部分）** | 用户退款后额度不会被收回 | 上量之后再做定期巡检 + 写负向 `refund` 分录 |
