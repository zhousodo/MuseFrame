## 二、已做的临时处置（2026-08-31）

按用户指示，**只摘上游密钥**，不动其它开关：

1. 备份：`/opt/museframe/.env.bak-20260831-180549`（`chmod 600`）。
   **⚠️ 2026-08-31 用户指示后已 `shred -u -z` 覆写删除**——服务器上不再有任何密钥副本
   （已全盘 grep 复核）。用户将改从管理后台自行配置。
2. 把 `.env` 里 `IMAGE_PROVIDER_API_KEY` 的值清空（保留变量名，便于原样贴回）。
3. `cd /opt/museframe && sudo docker compose up -d --force-recreate api`
   （⚠️ compose 的**服务名是 `api`**，`museframe-api` 是 container_name，用后者会报
   `no such service`，容器不会重建，旧密钥仍留在进程环境里。）

**为什么摘掉密钥就够**：`server/remoteAdapter.js` 的门禁是
`enabled = process.env.IMAGE_PROVIDER === 'remote' && !!cfg('image_provider_api_key')`。
密钥为空 ⇒ 远程适配器 `enabled=false` ⇒ **一个上游请求都不会发**，生成整体回落到
`LocalStyleEngine`（确定性像素引擎，零上游成本）。

**已验证**：容器内 `IMAGE_PROVIDER_API_KEY` 为空；容器 healthy；源站与公网 200。
另确认 `app_config` 表 **0 行**——密钥没有被写进运行时配置库（`configStore.js` 支持热改，
若库里有覆盖值，清空环境变量是无效的）。

## 三、⚠️ 补做：彻底堵死生成（2026-08-31 二次处置）

| 开关 | 新值 | 依据 |

| `ALLOW_GUEST` | `false` | `api.js:160` 无此项即抛 403 `AUTH_REQUIRED` |

按台账 append-only 的规矩**追加 `expire` 分录冲销**（`reference_key=lockdown_20260831_guest_revoke`），
不删任何历史行；动手前已 `cp -a` 备份整个 `museframe.db`。

**端到端实测**：游客换令牌 403 / 全站净额度 0 / 容器 healthy / 源站与公网 200
（站点仍可浏览风格，只是无法生成）。

⚠️ **异常信号**：2026-08-31 09:37–10:04 半小时内新建 7 个游客账号，节奏可疑，建议复核来源。

## 四、恢复付费上游之前，必须先堵住游客循环

> **✅ 2026-08-31 已在代码层堵上，详见 §八。** 本节保留当时的判断作为记录；
> 其中三种堵法现在是「可选的更严设置」，不再是恢复密钥的前置条件。

**只摘密钥是止血，不是堵洞。** 密钥一贴回去，白嫖路径原样复活。恢复前至少做到其一：

- `ALLOW_GUEST=false` + `FREE_REQUIRES_AUTH=true` — 必须登录才发免费额度。
  但邮箱可无限注册的话，每个新邮箱仍能白嫖 1 张，需配合邮箱域名限制或人工放号。
- 或整站 Basic Auth（照 `markstats` 的做法在 Caddy 上加一层），内测期最稳。
- 或把 `FREE_UNITS` 改 0，只让已购买/已配额的账号能生成。

改完记得 `docker compose up -d --force-recreate api`（服务名 `api`）。

## 五、顺带发现的问题

**3 个生成任务卡在 `running`**（`IMAGE_PROVIDER_TIMEOUT_MS=420000`）。多半是 worker 重启
留下的僵尸任务。需要确认它们是否已 release 掉预留额度——按 spec §13.4 失败应当释放预留，
但卡在 running 的任务既没成功也没失败，预留可能一直挂着。建议清理时一并核对
`credit_ledger` 的 reserve/commit/release 是否配平。

## 六、恢复密钥的操作

> ⚠️ **备份已按用户指示销毁，下面这段基于备份的恢复方式已失效。**
> 用户将从管理后台（`configStore` 支持热设，改完下一个请求生效、无需重启）自行配置。
> **注意：从后台设置会把密钥写进 `app_config` 表，届时清空环境变量将不再生效**——
> 因为 `cfg()` 优先读库、再回落环境变量。要再次断开上游，必须清库里的值，
> 或把 `IMAGE_PROVIDER` 改成 `local`。

### （已失效）原基于备份的恢复方式

```bash
# 从备份里取回（不要 echo 到终端/日志）
sudo grep '^IMAGE_PROVIDER_API_KEY=' /opt/museframe/.env.bak-20260831-180549 \
  | sudo tee /tmp/k >/dev/null
sudo sed -i "/^IMAGE_PROVIDER_API_KEY=/d" /opt/museframe/.env
sudo sh -c 'cat /tmp/k >> /opt/museframe/.env' && sudo rm -f /tmp/k
cd /opt/museframe && sudo docker compose up -d --force-recreate api
```

密钥也可经管理接口热设（`configStore` 支持，改完下一个请求生效、无需重启）——
但那会把密钥写进 `app_config` 表，届时**清空环境变量将不再生效**，需一并清库里的值。

## 七、代码层修复（2026-08-31，本仓库）

原先的行为是：`remoteConfig.enabled=false` 时 worker **静默回落 `LocalStyleEngine`**，
任务照样 `succeeded`、照样扣一张额度。也就是「后台不配密钥，服务看上去完全正常」——
产出的却是本地滤镜、不是模型结果。这既掩盖了配置缺失，也等于拿滤镜图收用户的额度。

现在改为**硬门禁**（`server/engine/remoteAdapter.js` 的 `generationStatus()` 是唯一判定源）：

| 位置 | 行为 |
|---|---|
| `POST /v1/generation-jobs` | 未配置 ⇒ **503 `GENERATION_UNAVAILABLE`**，在建任务与预留额度**之前**就拒 |
| worker `processJob` | 每个任务开跑前重查 ⇒ 未配置则 `failJob('GENERATION_UNAVAILABLE')` 并 `releaseUnits` |
| `GET /v1/discover`、`/v1/auth/config` | 返回 `generation.available` |
| 客户端 `web/app.js` | 不可用时按钮置灰「Generating is paused」，文案写明不扣费 |
| 管理后台 `web/admin.html` | 概览 / 配置页顶部状态横幅，直接列出缺哪个配置项 |

判定规则：

- `IMAGE_PROVIDER` **默认值改为 `remote`**（原先未设置就等于走本地）。未设置 / 空值
  ⇒ 按 remote 处理 ⇒ 没密钥就停用。
- `enabled` 现在同时要求 **密钥和 base URL**（原先只查密钥，base URL 为空时每次远程调用
  必失败、然后悄悄落到本地引擎）。
- 只有显式 `IMAGE_PROVIDER=local` 才整条链路走本地像素引擎（开发/离线自测）。
- 新增后台开关 `local_engine_fallback`，**默认关**：远程失败即失败并退额度，不再用滤镜
  结果顶替模型输出。要恢复旧行为得手动打开，横幅会红字提示代价。

**顺带修掉了 §五**：卡在 `running` 的僵尸任务在 worker 重启时被重新入队，若此时未配置
密钥即判 `GENERATION_UNAVAILABLE` 并释放预留额度——挂着的预留会自己回到额度池。

已实测（本地隔离环境，非生产库）：

| 场景 | 结果 |
|---|---|
| remote、无密钥 | 建任务 503 `GENERATION_UNAVAILABLE`，额度 3→3 未动 |
| 后台热填 base URL + 密钥（不重启） | `available:true`，任务成功走远程，额度 3→2 |
| remote、上游不可达、fallback 关 | 任务 `failed / PROVIDER_TIMEOUT`，额度 3→3 **已退回**，无候选图 |
| remote、上游不可达、fallback 开 | 任务成功走本地引擎，额度 3→2（即旧行为，须显式打开） |
| `IMAGE_PROVIDER=local` | 正常生成，后台横幅显示「本地像素引擎模式」 |
| 卡住的 `running` 任务 + 重启且未配密钥 | 判 `GENERATION_UNAVAILABLE`，预留额度自动退回 |

**这一步没有动**：`ALLOW_GUEST` / `FREE_REQUIRES_AUTH` / `FREE_UNITS` 仍是原值。
游客循环白嫖在随后的 §八 里堵上。

## 八、堵住游客循环白嫖（2026-08-31，本仓库）

§一 记的白嫖路径是：`POST /v1/auth/exchange` 空 body 无凭据换令牌 → 用掉 1 张免费额度
→ 换一个新游客 → 循环，总量无上限。

根因不在「游客可以换令牌」，而在**免费额度的去重键会退化成 user_id**：

```js
const dedupeId = isGuest ? (deviceHash || userId) : userId;   // 旧代码
```

匿名调用者恰恰是「不带 deviceId」的那一类，于是 `deviceHash` 为空 → 退回 user_id →
每个新账号都是全新的键 → 每次都发。**去重键在最需要它的场景里失效了。**

### 现在的四道闸（`server/api.js` 的 `maybeGrantFree`）

任一不过就不发；账号照建，仍可登录、购买、浏览，只是没有免费张数。

| # | 闸 | 服务端可核实？ |
|---|---|---|
| 1 | 游客必须带设备指纹，**没有就不发**（不再退回 user_id） | 否，但只用来「更难拿到」，从不用来放行 |
| 2 | 同一设备 / 同一身份**只发一次，全局去重**（换新账号也不发） | 否，同上 |
| 3 | **单 IP 每 24 小时上限** `free_grants_per_ip_day`（默认 3） | ✅ 服务端观测 |
| 4 | **全站每 24 小时上限** `free_grants_per_day`（默认 50） | ✅ 服务端观测 |

第 4 条是关键：攻击者换设备号能绕 1、2，换 IP 能绕 3，但**换不掉全站天花板**——
最坏情况下每天的免费成本被钉死在 `free_grants_per_day × free_units` 张。用尽后自动停发，
滚动窗口到点自愈，无需人工干预。任一上限设为 0（或 `free_units=0`）即完全停发。

发放记录落在新表 `free_grants`（**不存原始 IP，只存加盐哈希**，盐取自 `ADMIN_TOKEN`）。
`credit_ledger` 里的历史 `grant:free_grant:*` 记录仍然参与去重，老用户不会被重复发放。

### 顺带发现并堵上的更大的洞：两个开发开关

生产 `.env` 里 `ALLOW_MOCK_PURCHASES=true` 和 `ALLOW_TEST_LOGIN=true` 都开着
（`OPS.md` §7 写的是生产必须 false，实际没关）。这两个比免费额度循环严重得多：

- `ALLOW_MOCK_PURCHASES=true` ⇒ 任何人 `POST /v1/purchases/verify`
  `{platform:'web', productKey:'mini_pack'}` 就能**凭空拿到整包付费额度**，
  不受任何免费额度上限约束。
- `ALLOW_TEST_LOGIN=true` ⇒ 任何人用 `provider:'dev'` + 任意邮箱就能拿到
  「已登录」账号，**连 `free_requires_auth=true` 都能绕过**。

现在两者除了 env 开关，**还必须带管理员令牌**（`X-Admin-Token`）才生效；
`/v1/auth/config` 也不再对公众声明 `billing.mock`（客户端因此隐藏演示购买入口，
改提示「请在手机 App 内完成购买」）。启动时若发现开关为 true 会打印告警，
后台横幅同步红字提示。**仍建议在生产 `.env` 里改成 false。**

### 后台可见性

概览 / 配置页新增第二条横幅：近 24 小时发放次数 / 上限、涉及多少个 IP、单 IP 上限、
是否已触顶、是否已完全停发，以及两个开发开关是否还开着。上限值在配置页热改、即时生效。

### 实测（本地隔离环境）

| 场景 | 结果 |
|---|---|
| `POST /v1/auth/exchange` 空 body（§一 的原始复现路径） | 令牌照发，**额度 0** |
| 上述空 body 循环 5 次 | 共拿到 **0** 张 |
| 正常客户端（带 deviceId） | 第一次 1 张，同设备再来 **0** 张 |
| 同 IP 轮换 10 个设备号 | 只发到单 IP 上限 3 张就停 |
| 抬高 IP 上限、全站上限设 2，尝试 5 次 | 发 1、1、0、0、0，`capReached=true` |
| 上限设 0 | 一张不发，后台显示「免费额度已停发」 |
| 演示购买（无管理员令牌 / 有） | 422 拒绝 / 200 verified |
| `/v1/auth/config` 的 `billing.mock`（公众 / 管理员） | false / true |
| 测试登录（无管理员令牌 / 有） | 403 AUTH_INVALID / 200 |
| 正常生成全流程回归（带 deviceId） | 任务成功，额度 3→2 |

另：`/v1/auth/exchange` 原有的 20 次/10 分钟/IP 限流仍在，是这四道闸之外的第五层。

### 结论

§四 列的三种运维堵法（`allow_guest=false`、整站 Basic Auth、`free_units=0`）现在是
**可选的更严设置**，不再是贴回付费密钥的前置条件。密钥贴回去之后，最坏日成本由
`free_grants_per_day` 封顶，随时可在后台调小或归零。
